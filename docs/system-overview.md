# Как устроено LLM-приложение с LangChain, LangGraph и LangSmith

Этот документ даёт общую картину системы, которую проект разбирает по отдельным исполняемым урокам. Он не предполагает, что языковая модель сама умеет вызывать Python-функции, хранить состояние или управлять workflow: всё это обязанности приложения вокруг модели.

## Четыре слоя

```text
┌──────────────────────────────────────────────────────────┐
│ LLM                                                      │
│ Получает сообщения и возвращает текст или tool request   │
├──────────────────────────────────────────────────────────┤
│ LangChain                                                │
│ Models, Messages, Tools, стандартные integration APIs    │
├──────────────────────────────────────────────────────────┤
│ LangGraph                                                │
│ State, Nodes, Edges, Loops, Checkpoints                  │
├──────────────────────────────────────────────────────────┤
│ LangSmith                                                │
│ Tracing, Datasets, Experiments, Evaluation, Monitoring   │
└──────────────────────────────────────────────────────────┘
```

Короткая backend-аналогия:

- **LangChain** — SDK и унифицированные интерфейсы для LLM-компонентов;
- **LangGraph** — state machine/workflow engine для долгоживущего поведения;
- **LangSmith** — distributed tracing и evaluation-инфраструктура для LLM-систем;
- **LLM provider** — внешний вычислительный сервис, который генерирует ответы и tool requests.

LangGraph использует типы сообщений и tools из экосистемы LangChain, но отвечает за другое: кто выполняется следующим и какое состояние переходит между шагами. LangSmith необязателен для исполнения — он помогает понять и измерить уже работающую систему.

## Сообщения вместо строк

Chat model получает последовательность типизированных сообщений:

```text
HumanMessage -> AIMessage -> ToolMessage -> AIMessage
```

`HumanMessage` содержит запрос пользователя. `AIMessage` может содержать обычный текст либо структурированный список `tool_calls`. `ToolMessage` содержит результат конкретного вызова и обязательно связывается с запросом через `tool_call_id`.

История сообщений одновременно является:

- контекстом для следующего model call;
- журналом уже выполненных действий;
- минимальным состоянием агента;
- материалом для трассировки и последующей оценки.

## Что происходит при tool calling

Tool — обычная функция с машинно-читаемой схемой имени, описания и аргументов. Когда приложение делает `model.bind_tools(...)`, модель получает эти схемы вместе с запросом.

Но binding не исполняет функцию:

```text
User question
      │
      ▼
LLM sees tool schema
      │
      ▼
AIMessage(tool_calls=[...])
      │
      │  только намерение
      ▼
Application validates arguments
      │
      ▼
Python executes tool
      │
      ▼
ToolMessage(tool_call_id=...)
      │
      ▼
LLM produces final answer
```

Граница принципиальна: LLM предлагает действие, а приложение решает, разрешено ли оно, валидирует аргументы, выполняет код, обрабатывает ошибку и возвращает наблюдение модели.

## Ручной agent loop

Минимальный ReAct-подобный цикл можно написать обычным Python-кодом:

```text
Think / model call
        │
        ├── no tool calls ──▶ final answer
        │
        ▼
Act / execute requested tools
        │
        ▼
Observe / append ToolMessage
        │
        └────────────────────▶ next model call
```

Это уже агентное поведение: модель выбирает следующий допустимый action на основании текущего состояния. Однако ручной цикл быстро усложняется, если появляются разные ветви, retries, human approval, persistence или параллельные шаги.

## Тот же цикл как LangGraph

LangGraph делает переходы явными:

```text
                ┌──────────────────────┐
                │                      │
                ▼                      │
START ──────▶ agent ──────▶ tools ─────┘
                │
                │ AIMessage без tool_calls
                ▼
               END
```

- `agent` вызывает модель и добавляет `AIMessage` в state;
- conditional edge проверяет `tool_calls`;
- `tools` исполняет запросы и добавляет `ToolMessage`;
- обратное ребро возвращает обновлённый state модели;
- отсутствие tool calls переводит граф в `END`.

Граф не делает модель умнее. Он делает control flow явным, проверяемым, расширяемым и наблюдаемым.

## State и persistence

Без persistence вызывающий код сам передаёт накопленную историю:

```text
Turn 1 result.messages
        +
new HumanMessage
        │
        ▼
Turn 2 invocation
```

Checkpointer позволяет графу сохранять state по `thread_id`:

```text
                 Checkpointer
               ┌──────────────┐
thread-a ──────▶│ messages A   │
thread-b ──────▶│ messages B   │
               └──────────────┘
```

Одинаковый `thread_id` продолжает беседу, разные identifiers изолируют состояния. `InMemorySaver` демонстрирует семантику, но не durability: данные исчезают после остановки процесса. Production-системе нужен внешний durable store и отдельная политика хранения данных.

## Reliability принадлежит приложению

Поскольку модель недетерминирована, приложение обязано ограничивать поведение:

- неизвестный tool не должен приводить к произвольному выполнению;
- tool arguments должны валидироваться;
- исключение функции должно стать понятным наблюдением или controlled failure;
- число шагов должно иметь верхнюю границу;
- credentials не должны попадать в prompts, логи или сообщения об ошибках;
- внешние действия повышенного риска требуют отдельного authorization layer.

В учебном графе ошибки tools превращаются в `ToolMessage(status="error")`, а recursion limit останавливает бесконечные запросы инструментов.

## Что добавляет LangSmith

Обычный пользователь видит только финальный ответ. Trace показывает траекторию:

```text
graph
├── agent / model call
│   └── tool request: search_docs(query="vacation")
├── tools
│   └── policy text
└── agent / model call
    └── final answer
```

Для каждого шага могут быть доступны inputs, outputs, duration, errors и token usage. Это помогает различить несколько классов проблем:

- модель не выбрала нужный tool;
- описание или schema инструмента неоднозначны;
- tool вернул плохие данные;
- state потерял важное сообщение;
- финальная генерация неверно интерпретировала корректный результат.

Tracing меняет наблюдаемость, но не функциональный control flow. Поэтому в проекте он добавляется после работающего графа и остаётся opt-in.

## От tracing к evaluation

Один trace отвечает на вопрос «что произошло в этом запуске?». Evaluation отвечает на другой вопрос: «стала ли новая версия лучше на репрезентативном наборе случаев?»

```text
Dataset
  ├── known policy
  ├── unknown policy
  ├── tool required
  └── tool not required
          │
          ▼
       Agent version
          │
          ▼
Metrics: answer correctness + expected tool use
```

Для LLM-приложения полезно отдельно измерять финальный результат и trajectory. Правильный текст, полученный через запрещённый или лишний tool, может быть функционально приемлем, но архитектурно неверен. И наоборот, правильный выбор tool ещё не гарантирует хороший ответ.

## Граница этого проекта

Учебный `search_docs` ищет по фиксированному словарю. Он нужен для понимания tool calling, а не для демонстрации retrieval quality. Проект сознательно не включает vector database, production RAG, web service, voice interface, multi-agent coordination и durable database persistence. Эти темы логично изучать после того, как базовый цикл сообщений, tools, state и routing перестал быть «магией».
